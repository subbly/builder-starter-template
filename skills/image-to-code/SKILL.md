# Image to code

A mockup is the contract: the user picked that exact image and expects the shipped section to come out very close to it, not pixel-perfect but unmistakably the design they chose, and every deviation they can spot at a glance reads as a broken promise that costs their trust. Match it in real markup, not pixels: composition, scale, palette, typography hierarchy, and background treatment come from the image unchanged, while text becomes real copy in real fonts, imagery becomes individually generated assets, and every element maps to DOM structure plain CSS can build.

The only licensed deviations are the mockup's own flaws: garbled text, unreadable contrast, an element no CSS can build. Keep the intent, fix the flaw in code, and tell the user what changed and why.

## Reading the mockup

An inspiration image may hold one section or a whole page; it is already in context. When the image was generated by `generate_design_inspiration_image`, its generation prompt is the written half of the contract: take hexes, font choices, and the signature move from the prompt rather than re-inferring them from pixels, and use the image for what the prompt cannot fix, composition and scale. A hero from that pipeline was composed to fill the viewport, so implement it at 100vh.

Walk the image region by region (headline, CTA, imagery, background, decorative elements), naming for each the markup and CSS that rebuilds it: grid or flex structure, explicit hexes, px type sizes, borders, shadows. A signature move (an oversized glyph, a bleed, type crossing a seam) survives at its original scale and position; toned down to comfortable, it is no longer the design that was picked.

Mockup copy is a stand-in: write real copy, short and concrete, free of marketing filler. Fonts follow the user's request first, the closest real webfont to the mockup's type otherwise. What the image cannot show (hover, focus, motion) is designed in the Motion section below, not skipped.

## Combining inspirations into one page

A whole-page image already settles the combination: sections, order, and seams come from it. When each section is a separate image, the implementation must be seamless: nothing on the page may reveal that the sections were designed in isolation.

- Tokens are global: one palette, one type scale, one spacing rhythm shared by every section, never re-derived per image.
- Mind the seams: where two sections meet, the background treatments must meet deliberately (a shared fill, a clean hard edge, or a gradient landing on the neighbour's hue), never two near-identical tones that read as a rendering mistake.
- The hero leads: where a section's inspiration drifts in style, the hero wins.

## Down to mobile

When a mobile mockup exists, it is the mobile contract and gets the same region walk. Otherwise mobile is derived, not shown: design it rather than leaving it to the browser.

- Reflow, don't shrink: multi-column grids collapse to a single column in reading order, and side-by-side splits stack; text precedes its supporting image unless the image is the point.
- Hierarchy survives the drop: type scales down but keeps its contrast, so display type stays display-sized relative to body.
- The signature move adapts rather than disappears: an oversized glyph or a bleed shrinks or repositions to keep its effect on a narrow canvas.
- Crowding is the failure: keep the spacing generous through the collapse, and drop or simplify whatever fights for room (decorative elements follow their mobile plan from the asset planning).
- Full-bleed imagery re-crops for portrait: pick the crop that keeps the subject, never the center by default.

## Motion

Animate effects and micro-interactions as part of the implementation, following the mockup's character: expressive where it is loud, subtle where it is quiet. Prioritize CSS-only solutions for plain HTML, and use the Motion library for React when it is available.

Focus on high-impact moments: one well-orchestrated page load with staggered reveals (`animation-delay`) creates more delight than scattered micro-interactions. Beyond the load, reach for scroll-triggered animations and hover states that surprise.

## Planning the assets

Enumerate every image each section needs: main section image, icons, logos, decorative shapes, background ornaments. For each asset decide:

- Compose, don't stack: assets that always render together as one visual become a single generated image, so the composition stays exactly as the mockup shows it and the alignment, scale, and color-bleed issues of stacked layers disappear. Split into separate assets only when the layers genuinely move, animate, or render conditionally.
- Transparent or solid: transparent for logos, icons, decorative or floating assets, and background ornaments that overlay the page. A transparent asset composes over any background; a solid one with a near-but-not-exact background color leaks a visible seam the moment the page background shifts, and similarity is never a match. Solid is reserved for product photography and images meant to read as contained, bordered tiles; an asset sitting directly on the page without a container is not solid. When in doubt, transparent.
- Customer avatars are never generated: render placeholders instead (gradient circles, initials, generic portraits).
- Every decorative element gets a mobile plan: reposition or shrink at a breakpoint, hide below one, or swap for a simpler variant. Implement the breakpoint behaviour, not just the desktop layout.

## Generating the assets

- `generate_image` is the production tool, `generate_design_inspiration_image` only makes mockups. When the mockup was generated, every asset is made with `generate_image` to replicate the picked design, and `get_stock_image` is not an option: stock cannot match imagery the user already approved. Prefer generation over stock for outside images too, since generated assets stay on-brand and stock does not.
- Pass the section's inspiration image on every call via `referenceImages` so the asset stays on the picked direction; add further entries (logo, product photo) when the asset must also match those.
- Transparency is a parameter, not prose: pass `background: "transparent"` and keep the prompt silent about it. Sizing, quality, and format: follow the tool description.
- Render with `url`, read with `path`: markup (`<img src>`, `next/image`, CSS `background-image`) always gets the CDN `url`; the local `path` is for `read_file` only and 404s over HTTP.
